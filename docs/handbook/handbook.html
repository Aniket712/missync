1  The problem

Data platforms are webs of dependencies. A table feeds a view; the view feeds a dashboard; the dashboard feeds a weekly finance report; a machine-learning job reads the same view. Most of these links are implicit: nobody wrote them down, and the database does not enforce them. When an engineer changes the table, nothing tells them what is downstream.

The four failure modes this project targets

Failure modeWhat happensTypical cause
Structural breakA column or table disappears or changes type; a downstream view, query or job errors out — or worse, silently casts.DROP / RENAME / ALTER TYPE
Missing recordsThe schema is fine but rows vanish: a join becomes inner, a filter is too broad, a cleanup deletes real customers.DELETE, join/filter changes
Metric driftNothing fails. The headline number simply moves (here +7%) because a definition changed.Redefined views, status filters
Data-quality regressionNULL rates jump, keys duplicate, values change — the pipeline is "green" but the data is worse.Backfills, lookups with partial coverage
Why this is hard (1) Reviewers read a diff of SQL, not a diff of consequences. (2) Tests that exist check what someone thought of in advance. (3) Staging copies are expensive, stale, or missing. (4) Lineage is scattered across view definitions, BI tools and people's heads. The result: breaking changes are found by the people who consume the data, after deployment.

What a good answer must do

  • Predict what a change will touch before it runs (static analysis).
  • Measure what it actually does — without risking production.
  • Separate measurements from guesses, and say how sure it is.
  • Not cry wolf: a difference is not automatically a defect (a deliberate DELETE should remove rows).
  • Admit gaps: unknown consumers, unreadable view definitions, sampled data.

2  The solution at a glance

Missync is a web application that takes a proposed SQL change, analyses it statically, applies it to a disposable copy of the data, compares before and after, traces what depends on the changed objects, and produces an evidence-based report. The source database is only ever read.

Design principles (the "personality" of the tool)

PrincipleHow it shows up in the product
Never touch productionRead-only connectors; candidate SQL runs only in an in-memory DuckDB with file/network access disabled.
Predicted ≠ verifiedEvery finding carries a badge: Verified in sandbox or Predicted.
Evidence over scoresSeverity is rule-based (Critical…Info) with the measured numbers attached; there is no opaque "risk score 73".
A difference is not a defectA May be intended tag when the statement plausibly explains the change (e.g. a filtered DELETE).
Honest about gaps"Lineage incomplete", "sampled to N rows", "not validated — static only" appear in the UI and the reports.
LightweightOne Python process + SQLite metadata store + static UI. No agents, no catalog, no warehouse write access.

3.4  Why it is lighter and (in this niche) better

  • One process, one container. FastAPI serves the API and the built UI; metadata lives in a small SQLite file. No Kafka, no crawler fleet, no graph database.
  • No write access, no staging warehouse. The sandbox is in-memory DuckDB, so it needs no cloud spend, no cloning permissions and leaves nothing behind.
  • No framework adoption. Works with a pasted ALTER TABLE as readily as with a view rewrite.
  • Honest output. It refuses to claim safety ("not a guarantee"), refuses unreliable comparisons (non-unique keys) and shows where lineage is incomplete.
  • Same engine everywhere. The public demo and the self-hosted app run the identical analysis code — the demo is not a mock.
  • Hackable. ~5k lines; a connector is ~100 lines; rules live in one readable file (severity.py).
Where the others are genuinely better (be fair) Datafold and SQLMesh scale to very large tables and have mature CI/merge-blocking; DataHub/Atlan cover enterprise lineage across hundreds of sources and BI tools; Monte Carlo watches production continuously, which Missync does not do at all. Missync is a pre-change inspector, not a catalog or an observability platform — it complements them.

4.2  The analysis pipeline (sequence)

4.2a  Jobs, progress and limits

The UI does not hold one long request open. POST /api/jobs queues the analysis on a small worker pool (MISSYNC_MAX_CONCURRENT_ANALYSES, default 2; extra requests wait as queued). The engine reports a stage and percentage between its steps (parse, read schema, copy sample, profile, apply, compare, reconcile, trace impact), the UI polls GET /api/jobs/{id} to draw the progress bar, and DELETE /api/jobs/{id} cancels the run at the next step boundary. An overall deadline (MISSYNC_ANALYSIS_DEADLINE_S, default 600 s) stops runaway analyses. POST /api/analyses still exists as a synchronous call for scripts; it uses the same pool, so concurrency stays bounded either way. The command line (missync analyze) calls the engine directly without the server.

Key trade-offs decided during the build

DuckDB as a universal sandbox instead of cloning each database. Pros: no write privileges or infrastructure; isolated by construction; identical behaviour for every source. Cons: constraints, triggers, indexes and engine-specific semantics are not reproduced; large tables are sampled. Mitigation: sampling and dialect differences are disclosed as limitations and lower confidence.
Cloud warehouses: static + dry-run only. Copying warehouse tables is slow and costly, so BigQuery and Snowflake never run the sandbox; results are labelled "predicted".
Separate "dialect of the change" input. The SQL a user proposes (e.g. PostgreSQL ALTER … TYPE) can differ from the source's own dialect (SQLite for the demo), so the request carries both.
SQLite for metadata. Zero-ops persistence suits a single-instance tool. Trade-off: one writer; fine for the intended scale.

6  How it was built, step by step

The build followed a plan agreed before any code was written (written to a plan file and approved), then proceeded in layers from the inside out: the safest, most testable code first, the UI last.

Step 0 — Plan and environment

  • Inspected the repository (empty) and the toolchain: Python 3.12 and Node were present; Docker was not. That one fact shaped later decisions (use DuckDB as the sandbox; find another way to test Postgres).
  • Wrote a build plan: monorepo layout, sandbox strategy, evidence labelling, demo-mode rules, build order, verification criteria.
  • Network was flaky: package installs needed long timeouts and retries — handled by installing core packages first and optional connector libraries one by one.

Step 1 — Foundations (models.py, config.py, security.py)

  • Pydantic models for schema snapshots, findings, impact graph, requests and results — the vocabulary every other module speaks.
  • Settings from MISSYNC_* env vars (mode, data dir, limits, host policy).
  • Security helpers written first: secret redaction + a logging filter, Fernet encryption, SSRF host validation, data-dir path confinement, identifier quoting.

Step 2 — Connectors (connectors/)

  • A small abstract Connector (test, discover, bounded fetch_rows, optional query) plus a Capabilities declaration.
  • SQLite (mode=ro + query_only), DuckDB (read_only=True; CSV/Parquet exposed as views), PostgreSQL (SQLAlchemy; read-only session; statement timeout), BigQuery and Snowflake (official clients, imported lazily).
  • A registry (build_connector) that validates required parameters and applies path/host policy.

Step 3 — Static analysis

  • sql_parser.py: parse with SQLGlot, classify each statement, extract structural changes (drop_column, alter_type, rename_column, delete_rows …) and flags such as "no WHERE". assert_single_select guards metric/ad-hoc queries.
  • schema_diff.py: normalise types into families, classify a change as widening / narrowing / incompatible, diff two snapshots, hash a stable schema signature.
  • lineage.py: from view definitions build table-level and column-level edges (SQLGlot lineage()); add user-registered assets; mark views whose lineage is incomplete; compute downstream impact by graph traversal.

Step 4 — Dynamic analysis

  • sandbox.py: copy bounded samples via a temp CSV and COPY (fast, type-cast by DuckDB), create base and cand schemas, recreate views in both, then lock down (enable_external_access=false, lock_configuration=true). Apply transpiled statements to cand only, with a timeout thread calling interrupt().
  • profiling.py: per-column null counts/rates, distinct counts, min/max/avg/sum, per-key duplicate groups; compare_profiles for before/after.
  • reconcile.py: anti-joins and an IS-DISTINCT-FROM row comparison, only when the key is unique in the baseline.

Step 5 — The engine (engine.py, severity.py)

  • Orchestrates steps 3–4, turns measurements into Finding objects, merges predicted and verified results, escalates severity when dependents exist, builds the impact graph and a plain-language verdict.
  • Rules live in severity.py as small pure functions so each is unit-testable and readable.
  • First end-to-end run of the four scenarios exposed the first real bug (see the table below).

Step 6 — Persistence, API, reports, UI

  • Store: SQLAlchemy tables for connections (encrypted params), assets, baselines, analyses.
  • API (api/app.py): connections, schema, lineage, assets, analyses, scenarios, baselines, report downloads; demo-mode guard; serves the built UI.
  • Reports: JSON (versioned) and a self-contained HTML report with light/dark CSS, escaping and a strict CSP header.
  • Frontend: Overview, Connections, Analyze, Result (tabs), Baselines, History; lazy-loaded graph; light/dark theme.
  • Demo data: deterministic generator (seeded RNG) for a synthetic shop: customers, products, orders, order_items, segment_map, three views and four registered assets; four scenarios.

Step 7 — Verification and hardening

  • 70 automated tests at the time of the first edition (now 98 backend tests); then a real PostgreSQL 16 and a real Chromium were added to check what had only been assumed.
  • Screenshots were inspected; layout problems were found and fixed (below).

Step 8 — Making it releasable (after the first edition)

  • UI-driven connections. A guided connector picker, URL paste, a one-click embedded sample PostgreSQL (pgserver, no Docker), a separate Test connection step with server version and latency, readable errors, row preview and schema search.
  • Hardening. Optional bearer-token auth and a refusal to listen on a non-local address without it; per-connector parameter whitelists; connecting to the validated IP (DNS-rebinding guard); request-size cap; request ids, security headers and a global error handler.
  • Reliability. Background jobs with progress, cancel, bounded concurrency and a deadline; SQLite WAL with a busy timeout; schema versioning with migrations; history retention; /api/ready; Postgres row counts from planner estimates instead of a full count per table.
  • Integration. missync analyze for CI (folder of migrations, --fail-on exit codes, JSON/HTML reports) and a composite GitHub Action.
  • Packaging and project files. A missync command, the UI bundled into the wheel (this also fixed the UI not being found in a non-editable install), install.sh, a release script, CI workflows, LICENSE, SECURITY, CONTRIBUTING and CHANGELOG.

7  The analysis engine in depth

7.1  Static analysis: what is recognised

SQLRecognised asPredicted consequence
ALTER TABLE t DROP COLUMN cdrop_columnConsumers of t.c break (High, escalated if dependents exist)
ALTER COLUMN c TYPE xalter_typeClassified widening / narrowing / incompatible from declared types
RENAME COLUMN / TABLErename_*Same as removal for old name
DROP TABLE / VIEWdrop_objectEverything reading it breaks

7.2  Type-change classification

7.3  Lineage and impact

  • Edges come from SQLGlot's lineage() run on each view output column against the discovered schema; leaves that resolve to a known table.column become column edges.
  • Impact is a breadth-first walk from the changed objects. Whole-object changes cascade to every dependent; column changes follow only column edges (plus "possible" edges through unreadable views).
  • Registered assets match when they depend on a changed column, an impacted column, or an impacted object. A table-level dependency with column-level change is reported as "column usage unknown".

7.4  Severity rules (all of them)

SignalSeverity
Removed/renamed table or columnHigh
Type change: narrowing or incompatible / wideningHigh / Low
NOT NULL addedMedium
UPDATE/DELETE without WHEREHigh
Rows lost (verified): ≥ 10% / > 0High / Medium
Records missing by key: ≥ 5% / > 0High / Medium
NULL-rate increase (percentage points): ≥ 20 / ≥ 5 / > 0.1High / Medium / Low
New duplicate keysHigh
Metric drift: ≥ 10% or ≥ 10× tolerance / > toleranceHigh / Medium
A view stops binding after the changeHigh
Escalation: a dependent view or registered asset is affected+1 level (cap Critical)
No arbitrary scoreThresholds are deliberately few, visible and editable in one file. Each finding shows the measured numbers that triggered it, so a reader can disagree with the rule — not just with a number.

7.5  Reconciliation and its safety rule

For each table with a key (declared, or primary key), Missync counts matched keys, keys missing after the change, keys new after the change, and matched rows whose values changed (per column, values compared as text so a pure type change is not reported as a value change). If the key is not unique in the baseline, the comparison is refused with the reason — an unreliable comparison is worse than none.

7.6  The evidence model

FieldMeaning
kindverified = measured in the sandbox; predicted = from static analysis only
confidencehigh = full copy of the table; medium = sampled data or measured through a recreated view; low = lineage incomplete / static only. A one-line reason is stored.
possibly_intendedThe statement plausibly explains the difference (e.g. rows lost after a filtered DELETE). Shown as a tag, severity unchanged.
limitationsWhat this particular finding cannot tell you.
evidenceThe raw numbers (counts, before/after rates, example keys).

7.7  Baselines

A baseline stores a schema snapshot, its SHA-256 signature (names, types, nullability, view SQL — formatting noise in view SQL is normalised away) and a profile of the sampled data. Comparing a baseline to "now" or to another baseline re-uses the same diff and finding code, plus an explicit limitation that growth in row counts between two dates is often normal.

Honest limitsThere is one shared access token and no user accounts, roles, audit log or per-user history: anyone with the token can use every saved connection and see every analysis. Missync is designed for your own machine or a trusted team network; put TLS (a reverse proxy) in front before exposing it further. A public multi-visitor deployment would additionally need per-visitor isolation and rate limiting, which are not built. See SECURITY.md.

12  Running, configuring and extending

12.1  Run it

Requires Python 3.11+ and Node 18+. The shortest path, from the repository root:

.\start.ps1        # Windows PowerShell
./install.sh       # macOS / Linux
# then open http://localhost:8000

Both scripts do the one-time setup (virtualenv, PostgreSQL driver, embedded sample database package, built UI) and start Missync in self-hosted mode so connections can be added in the UI. If a virtualenv already exists, run pip install -e "backend[postgres,sample]" once. Manual steps and the locked public-demo variant:

# Windows PowerShell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -e "backend[dev]"
cd frontend; npm install; npm run build; cd ..
python -m missync                      # UI + API at http://localhost:8000 (same as: missync serve)

# macOS / Linux / Git Bash
python -m venv .venv && source .venv/bin/activate
pip install -e "backend[dev]"
(cd frontend && npm install && npm run build)
python -m missync --port 8000 --data-dir ./data
Shell pitfalls. .venv/bin/activate does not exist on Windows (use Scripts); VAR=value cmd is Bash-only; && fails in Windows PowerShell 5.1. python -m missync avoids all three.

Development: npm run dev in frontend/ (port 5173, proxies /api to 8000).

12.1a  Command line and CI

missync analyze --sql change.sql --postgres-url "$STAGING_URL" --fail-on high
missync analyze --dir migrations/pending --sqlite ./app.db --format html --output report.html
missync analyze --connection "Staging" --sql change.sql   # a connection saved in the web app
missync analyze --demo --sql change.sql                   # try it on the bundled database

Exit code 0 means no finding at or above --fail-on (default high), 1 means there is one, 2 is a usage or runtime error. Set MISSYNC_POSTGRES_URL instead of passing the URL on the command line so the password stays out of process lists. The repository root contains a composite GitHub Action (action.yml) that runs the same command, writes the summary to the job summary and uploads the HTML report; see docs/CI.md. The action and workflows have not yet been run on GitHub.

12.2  Self-hosted with PostgreSQL sample data

cp .env.example .env
docker compose up --build       # Missync :8000, sample Postgres 127.0.0.1:5433

In Connections: host postgres, database shop, user missync_ro, password missync_ro_dev_only. The container binds 0.0.0.0 but the compose file publishes the port on 127.0.0.1 only and sets MISSYNC_ALLOW_INSECURE_BIND for that reason; if you publish it elsewhere, set MISSYNC_API_TOKEN and remove that line. 12.6  Typical extensions

  • New rule: add a pure function in severity.py, call it from engine.py, add a boundary test.
  • New connector: see chapter 10.
  • New finding type: produce a Finding in _data_findings or _structure_findings with kind, confidence reason and recommendation.
  • Register real consumers: assets are stored per connection (depends_on accepts table or table.column); a future import from dbt manifests or BI exports fits here.

13  Limitations and roadmap

Known limitations

  • Sandbox ≠ production engine. DuckDB does not reproduce constraints, triggers, indexes, collations or engine-specific functions. Failures caused by those will not show up; differences may appear that production would not have.
  • Sampling. Tables over the cap are sampled (first N rows, not random); results are labelled medium confidence.
  • Invisible consumers. BI tools, notebooks, ad-hoc queries and anything not registered or not in view SQL are unknown.
  • Static-only clouds. BigQuery/Snowflake produce predictions without data measurements.
  • Dialect coverage depends on SQLGlot; unusual syntax may fail to parse and is reported, not guessed.
  • One shared token, no accounts. There are no users, roles or audit log; history and connections are shared by everyone with access. Not suitable as a multi-visitor public service without further isolation and rate limiting.
  • Estimated row counts. PostgreSQL discovery uses planner statistics (marked ~); they can lag until the table is analyzed. The analysis itself counts the sandbox copy exactly.
  • Baseline growth. Row-count changes between dates may be legitimate growth.
